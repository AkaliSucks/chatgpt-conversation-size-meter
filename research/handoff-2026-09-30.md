============================================================
1. PROJECT PURPOSE
============================================================

We are reverse-engineering / empirically studying why some very long ChatGPT conversations eventually show the red:

"You've reached the maximum length for this conversation"

banner.

This is NOT an attempt to claim an official OpenAI limit.

The project is a Tampermonkey userscript called:

ChatGPT Conversation Size Meter

It captures ChatGPT conversation state, topology, retained/tool/image state, request lifecycle, transport behavior, SSE completion, and MAX-banner state so we can compare healthy conversations against conversations that hit MAX.

The important research shift is:

Earlier versions focused heavily on static conversation size.

Recent evidence shows static size alone is NOT sufficient.

We now need clean runtime/event data:
- real generation attempts
- send intent
- preflight
- generation dispatch
- SSE
- SUCCESS
- MAX condition
- blocked-before-dispatch behavior
- fresh source snapshots attached to the correct event

6. EMPIRICAL FINDINGS — STATIC LIMIT THEORY
============================================================

Several earlier observations invalidated a simple universal static threshold.

Examples:

MOA healthy:
- over ~1M user/assistant token estimate in older tests

Cat Co-op healthy:
- hundreds of thousands of display-like tokens
- very high node counts
- still generates successfully

GPU MAX:
- much smaller visible transcript than some healthy chats
- around ~7 MB retained proxy in an earlier representation
- had many image/tool states

Washer:
- healthy near ~6.8 MB retained
- MAX around ~7.29 MB
- later worked again around ~7.2 MB
- showed that MAX may be transient/recoverable

Lian Li:
- DIRECT representation around:
  5.96 MB retained
  12.78 MB active
  2,484 nodes

- BATCH representation around:
  12.29 MB retained
  20.08 MB active
  4,008 nodes

The same Lian Li representation has appeared as both stable and MAX.

Therefore:
- no universal retained-byte threshold has been established
- no universal visible-token threshold has been established
- no universal node-count threshold has been established
- static snapshots are "raw material", not necessarily the actual runtime limit

Old risk bands:
- Low <5 MB
- Elevated 5–6
- High 6–6.5
- Very High 6.5–7
- Observed MAX >=7

must no longer be presented as predictive truth.

They were experimental heuristics and are empirically falsified as a universal model.

11. FULL V2.22 AUDIT — MAIN PROBLEMS
============================================================

A full audit was completed before V2.23.

Main issues:

1. MAX conditions are being modeled as fake response attempts.

Need:
REAL ATTEMPTS
separate from
MAX EPISODES.

2. Repeated observation of the same visible MAX condition creates duplicate MAX attempts/events.

Need episode-level deduplication.

3. MAX banner detection is too broad.

Current-style whole-body text searching can potentially match:
- quoted conversation content
- our own discussions
- diagnostics
- assistant messages

Need actual visible non-conversation UI error/banner detection.

4. Raw stream text matching can false-positive.

Assistant content discussing:
"maximum length for this conversation"

must NOT itself mark MAX.

5. Meter-generated Retry Capture fetches pollute application telemetry.

Critical issue:
Retry Capture goes through wrapped `page.fetch`.

Then:
- normal fetch hook may inspect it
- explicit capture code may inspect it again

This can:
- double-process responses
- contaminate network metrics
- make giant full-conversation GETs look like generation network traffic

This likely explains weird values such as:
- generation response only ~9 kB
- "network max" ~20 MB

6. Generation transport, app-state traffic, and meter-generated capture traffic are mixed.

Need three separate categories:
- GENERATION TRANSPORT
- APP STATE NETWORK
- METER CAPTURE NETWORK

7. Old static LOW/ELEVATED/HIGH/MAX ZONE labels are misleading.

Demote/remove predictive framing.

Expose raw STATIC STATE VECTOR instead.

8. Null numeric bug exists.

JavaScript:
`Number(null) === 0`

Missing metrics must not silently become green/LOW.

9. SSE SUCCESS is finalized before transport telemetry is completely finished.

Outcome confirmation and telemetry closure need to be separate.

10. Benign `BodyStreamBuffer was aborted` after valid SSE completion should update the completed attempt rather than disappear.

11. Post-outcome capture race.

After SSE SUCCESS:
- UI may still look generating
- fallback logic may create a new current attempt
- scheduled post captures may attach incorrectly or fail to attach

12. Generation peaks remain blank because lifecycle phase relies too heavily on DOM Stop-button state.

An active real network generation should itself imply INFLIGHT.

13. MAX snapshots can be stale.

A newly detected MAX episode must not silently borrow a prior MAX snapshot from hours earlier.

14. SECURITY/PRIVACY ISSUE:
Diagnostics currently expose complete WebSocket URLs containing:
`verify=<token>`

These must be redacted before storage and diagnostics.

Also remove arbitrary WebSocket content previews.

15. Preflight matching is too time-based.

Prefer:
- conversation ID
- parent message ID
- action

then recency fallback.

16. Real generation request classification is too broad.

Require generation-shaped request structure.

17. Scheduled delayed captures are not bound strongly enough to the originating conversation.

If the user navigates to another chat before the timer runs, it could capture the wrong chat.

18. Persistent attempt state can become large.

Need bounded retention and visible storage-health errors rather than silently swallowing localStorage failures.

============================================================

Do not make SUCCESS detection slower.

If SSE emits:
- `finished_successfully`
- `message_stream_complete`
- `[DONE]`

the attempt may be marked SUCCESS immediately.

But do NOT stop tracking that attempt.

Separate:
- outcome status
- outcome confirmed timestamp
- outcome confirmation source

from:
- transport closed timestamp
- telemetry finalized timestamp

Later clone-stream close/errors should update the already archived attempt by ID.

`BodyStreamBuffer was aborted`

occurs after valid completion evidence:
- preserve error text
- mark benign
- keep SUCCESS

============================================================
16. V2.23 — NETWORK SEPARATION
============================================================

This is critical.

Separate:

GENERATION TRANSPORT
- `/backend-api/f/conversation` request body
- response SSE
- chunks
- bytes
- TTFB
- completion/error events

APP STATE NETWORK
- ChatGPT's own conversation GET/BATCH state requests

METER CAPTURE NETWORK
- explicit Retry Capture / forced state fetches created by the userscript

Retry Capture must:
- be processed exactly once
- still feed the conversation parser
- NOT count as generation transport
- NOT inflate generation "network max"
- NOT create a real attempt
- NOT create a new MAX episode

Prefer keeping a reference to original/unwrapped fetch for meter-internal captures, or explicitly tagging/excluding them.
