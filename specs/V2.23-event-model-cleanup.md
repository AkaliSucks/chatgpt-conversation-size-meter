PRIMARY GOAL
============================================================

V2.23 is NOT another prediction/risk-score version.

Its purpose is to make the collected SUCCESS/MAX data trustworthy by fixing event semantics, deduplication, self-generated measurement contamination, stale MAX attribution, privacy leakage, and attempt-storage issues.

============================================================
1. SPLIT REAL ATTEMPTS FROM MAX EPISODES
============================================================

Create two independent persisted state models.

A. REAL ATTEMPTS

A real attempt should exist only when there is actual send/generation intent, preferably an observed real generation request.

Example:

REAL ATTEMPT #17
- send intent timestamp
- prepare request
- prepare response
- generation dispatch
- request model
- request effort
- prompt chars
- SSE telemetry
- SUCCESS/MAX/ERROR outcome
- outcome confirmation source
- pre-attempt DIRECT/BATCH
- optional post-attempt DIRECT/BATCH
- timestamps

B. MAX EPISODES

A MAX episode represents the conversation-cap condition itself.

Example:

MAX EPISODE #4
- first banner-visible timestamp
- last banner-visible timestamp
- still active: yes/no
- related real attempt ID, if any
- blocked before dispatch: yes/no
- fresh DIRECT capture
- fresh BATCH capture
- banner cleared timestamp
- recovery confirmed later: yes/no
- capture history within episode

Do NOT create a fake “attempt” merely because the MAX banner exists.

Current bad behavior:
`#2 MAX`
`#3 MAX`
`#4 MAX`
etc.

All of those may actually be one continuous MAX episode.

============================================================
2. DEDUPLICATE MAX EPISODES
============================================================

Current V2.22 deduplication is wrong because fresh full captures have new `fullCapturedAt` timestamps, causing the same cap state to be counted repeatedly.

Implement episode-level deduplication:

- If a MAX episode is already active and the banner remains visible:
  - DO NOT create another MAX episode.
  - DO NOT create another synthetic attempt.
  - attach any fresh DIRECT/BATCH captures to the current episode.
  - update `lastSeenAt`.
  - update source-family capture data.

- Create a new MAX episode only after:
  1. prior episode has genuinely cleared, and
  2. a later distinct MAX condition appears.

Expose:
- total distinct MAX episodes
- current MAX episode active yes/no
- captures recorded inside current episode

Do not count every fresh source capture as a new MAX event.

============================================================
3. ADD SEND-INTENT DETECTION
============================================================

We need to distinguish:

A. user tried to send
B. actual `/f/conversation` dispatch happened
C. MAX blocked it before dispatch

Add a lightweight send-intent detector.

Possible signals:
- submit/send button click
- Enter-to-submit when composer is active
- other reliable current ChatGPT submit event

Do not interfere with submission.

Store:
- sendIntentAt
- composer text length if safely available
- conversation ID
- whether a real generation dispatch followed
- time from intent → dispatch

Then classify:

`BLOCKED BEFORE DISPATCH`

when:
- send intent occurs
- no real generation request follows in a short bounded window
- MAX banner appears

This is potentially critical for understanding hard-capped chats.

============================================================
6. SEPARATE METER-GENERATED NETWORK TRAFFIC
============================================================

This is critical.

Current Retry Capture traffic is going through the same wrapped `page.fetch` interception as application traffic.

`tryDirectURL()`:
- performs meter-generated GET
- wrapped fetch sees it
- response may be inspected by the normal hook
- `tryDirectURL()` then explicitly calls `inspectResponse()` again

This can cause:
- duplicate processing
- polluted network counters
- huge conversation-state responses appearing as “generation network max”
- misleading values like ~20 MB network max on a ~9 kB SSE response

Fix this.

Implement an explicit meter-internal fetch bypass or tag.

Preferred:
- retain a reference to the original unwrapped fetch and use it for meter-generated captures

or:
- mark internal meter fetches and exclude them from runtime attempt/network telemetry

Requirements:
- meter-generated Retry Capture requests may still feed the mapping parser exactly once
- they must NOT count as model-generation transport
- they must NOT inflate attempt network max
- they must NOT be double-inspected

Expose separate metrics:

GENERATION TRANSPORT
- generation request body
- SSE bytes
- SSE chunks
- WebSocket bytes related to generation
- generation-related HTTP responses

APP STATE TRAFFIC
- ChatGPT's own conversation state fetches

METER CAPTURE TRAFFIC
- Retry Capture / forced source snapshots

Never combine these into one ambiguous `network max`.

9. DO NOT STOP TELEMETRY WHEN SSE SUCCESS IS CONFIRMED
============================================================

V2.22 correctly finalizes SUCCESS from SSE completion, but it removes `store.current` immediately.

That means later:
- stream chunks
- stream close
- BodyStreamBuffer abort
- final byte counts
- transport events

cannot update the completed attempt.

Change this.

Separate:

A. outcome finalized
B. telemetry collection finished

When SSE says `finished_successfully`:
- immediately set outcome = SUCCESS
- set `outcomeConfirmedAt`
- set `outcomeConfirmedBy`
- UI can display SUCCESS immediately

BUT:
- keep a reference to that completed attempt available for stream telemetry updates
- update the archived attempt by ID when later stream chunks/end/error arrive
- only mark transport telemetry closed when the stream actually ends/aborts or a timeout expires

Fields:
- outcomeStatus
- outcomeConfirmedAt
- outcomeConfirmedBy
- transportClosedAt
- telemetryFinalizedAt
